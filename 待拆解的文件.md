# 1. 技术架构文档

## 1.1 系统定位

项目名称暂定：

```text id="ii8r0s"
Business Analysis Companion Workspace
```

中文定位：

```text id="potvpu"
商业分析伴随式工作区
```

系统不是一个独立 BI 系统，也不是 Claude Code 里的单个 Skill，而是一个基于 Claude Agent SDK 的商业分析工作区 harness。

Claude Agent SDK 官方文档说明，它提供 Claude Code 能力的 SDK 化接入，包括内置工具、hooks、subagents、MCP、permissions、sessions 等能力。([Claude][1]) 它还支持 streaming input mode，适合持久交互式 session、用户输入、中断、权限请求和 session 管理。([Claude][2]) 因此本系统以 Claude Agent SDK 承载 agent loop，以自有后端承载业务状态、工具执行、文件一致性和分析产物。

系统目标：

```text id="lhoxec"
让用户在已有个人助手工作流中，进入一个商业分析专用工作区；
保留自然语言协作体验；
补足数据上传、字段映射、任务进度、图表看板、报告生成、记忆复盘等结构化能力；
避免独立分析系统带来的数据迁移、结果导出和上下文割裂。
```

---

## 1.2 设计原则

### P1：Message-first，不是 Workflow-first

所有自然语言输入必须先进入统一消息入口：

```http id="x5wib1"
POST /api/agent/messages
```

不允许前端把普通自然语言默认发送到 `/api/agent/runs`。

每个 message turn 由后端 `MessageRuntime` 与 Claude Agent SDK 共同决定：

```text id="g4qyx5"
- 直接回答
- 追问澄清
- 读取项目状态
- 调用 business_analysis 工具
- 生成分析计划
- 启动分析任务
- 解释结果
- 生成报告
- 生成记忆候选
```

旧系统的问题正是 UI 看起来像 chat-first，但运行语义仍是 workflow-first；对话、agent run、commands 分散在多个入口里，缺少统一消息编排层。

---

### P2：Claude Agent SDK 是推理运行时，不是业务后端

Claude SDK 负责：

```text id="d91bsg"
- 多轮推理
- agent loop
- 工具调用决策
- session 连续性
- 用户级 / 项目级 Claude 配置加载
- permissions / hooks / MCP 生态能力
```

业务后端负责：

```text id="xaotj7"
- 项目状态
- 文件状态
- 数据 schema
- 分析任务
- 图表和报告产物
- 权限审计
- 记忆同步
- artifact manifest
```

Claude session 不能作为项目事实源。项目事实源必须是数据库和 workspace manifest。

---

### P3：外部只暴露一个业务工具

Claude Agent SDK 支持通过 in-process MCP server 定义自定义工具，让 Claude 调用应用内函数、API、数据库或领域逻辑。([Claude][3])

系统只向 Claude 暴露一个工具：

```text id="r6vc0f"
business_analysis(project_id, action, payload, reason)
```

不直接暴露几十个内部工具，避免工具上下文膨胀和权限失控。

---

### P4：Workspace 是项目事实源

每个项目都有独立 workspace：

```text id="e3rhnp"
workspaces/{project_id}/
  data/
  scripts/
  artifacts/
  reports/
  logs/
  .analysis/
  .claude/
```

其中：

```text id="codxsj"
.analysis/ 由系统读写，是项目事实源
.claude/   由 Claude 读取，是 agent 上下文和指令层
```

---

### P5：记忆同步必须受控

不能把所有分析过程自动写入用户级 Claude 记忆。系统必须先生成 memory candidate，再由用户确认是否同步。

```text id="ny090i"
默认：写入项目内记忆
可选：用户确认后同步到用户级 Claude memory
禁止：自动写入敏感原始数据、临时假设、中间错误结论
```

## 1.6 后端模块职责

### API Gateway

负责 HTTP API、SSE/WebSocket event stream、错误格式统一。

### Project Service

负责项目创建、项目状态、项目元数据。

### Workspace Manager

负责：

```text id="khn8je"
- 初始化 workspace 目录
- 保存上传文件
- 计算 checksum
- 维护 project_manifest.json
- 检测文件移动/修改/过期
- 生成 context_summary.md
- 管理 checkpoints
```

### Message Runtime

负责统一消息循环：

```text id="tffxks"
User Message
  → build context
  → send to Claude Agent SDK
  → receive assistant/tool events
  → if tool call, forward to Analysis Tool Gateway
  → persist events
  → stream to frontend
```

### Claude Runtime Adapter

封装 Claude Agent SDK，不允许业务代码到处直接调用 SDK。

方法：

```text id="p4xykc"
create_session(project_id)
resume_session(session_id)
send_message(session_id, message, context)
stream_events(session_id)
handle_tool_call(tool_call)
interrupt(session_id)
```

### Analysis Tool Gateway

统一执行 Claude 调用的 `business_analysis` action。

必须做：

```text id="ouel5q"
- action enum 校验
- payload schema 校验
- permission level 校验
- 审批判断
- tool call log
- job 创建 / 同步执行
- artifact 写入
- state patch
- structured ToolResult
```

### Job Orchestrator

负责长任务：

```text id="fsc0ei"
- panel build
- full pipeline
- report generation
- export
```

### Artifact Service

负责图表、表格、模型结果、报告文件注册和读取。

### Memory Bridge

负责：

```text id="b6xayx"
- 从项目结果生成 memory candidate
- 展示给用户确认
- 同步到项目内 memory
- 可选同步到用户级 memory
```

## 1.7 Claude SDK 配置建议

Claude SDK 应使用 streaming input mode。官方说明该模式适合持久交互、权限请求、中断和 session 管理。([Claude][2])

推荐默认配置：

```ts id="fzl6eq"
const options = {
  cwd: workspacePath,
  permissionMode: "dontAsk",
  allowedTools: [
    "mcp__business_analysis__business_analysis"
  ],
  mcpServers: [
    businessAnalysisMcpServer
  ],
  settingSources: ["user", "project"],
  systemPrompt: {
    type: "preset",
    preset: "claude_code",
    append: businessAnalysisSystemPrompt
  }
}
```

权限必须收紧。Claude SDK 提供 permission modes、permission rules 和 `canUseTool` runtime callback，用于控制工具使用。([Claude][4]) hooks 可用于工具调用前后、session start、execution stop 等事件拦截和审计。([Claude][5])

# 2. 数据模型文档

## 2.1 设计原则

```text id="ah72fs"
1. 数据库记录结构化状态。
2. workspace 保存真实文件和 artifact。
```

# 4. Coding Agent 一次性实现提示词

下面这段可以直接交给 coding agent 执行。

```text id="c6o4sr"
你现在是一名资深全栈架构师、Claude Agent SDK 集成工程师、数据分析平台工程师。请基于当前仓库，从零实现 Business Analysis Companion Workspace 的 MVP。不要沿着旧的 workflow-first 架构继续打补丁，而是按 message-first + Claude Agent SDK harness 的新架构重构。

【一、Git 管理要求】
1. 先执行 git status，确认当前工作区状态。
2. 不要覆盖用户已有未提交改动。
3. 新建或切换到分支：
   refactor/business-analysis-companion-workspace
4. 每完成一个稳定阶段提交一次 commit。
5. 最终输出：
   - 当前分支
   - git status
   - commit 列表
   - 主要文件变更
   - 测试结果
   - 未完成事项

【二、总体目标】
实现一个基于 Claude Agent SDK 的商业分析伴随式工作区：

Browser Web App
  → POST /api/agent/messages
  → MessageRuntime
  → ClaudeRuntimeAdapter
  → Claude Agent SDK
  → custom MCP tool: business_analysis
  → AnalysisToolGateway
  → internal analysis tools
  → workspace/artifacts/reports/memory
  → event stream back to frontend

核心原则：
1. 所有自然语言输入统一进入 POST /api/agent/messages。
2. 前端不再把普通自然语言默认发送到 /api/agent/runs。
3. Claude Agent SDK 是推理运行时，不是业务状态源。
4. 项目事实源是数据库 + workspaces/{project_id}/.analysis/project_manifest.json。
5. 外部只暴露一个工具 business_analysis。
6. 内部工具由 AnalysisToolGateway 分发。
7. 记忆同步必须生成 candidate 并等待用户确认。
8. 工具调用、job、artifact、approval、memory 都必须可追踪、可审计。

【三、推荐技术栈】
优先复用当前仓库已有技术栈。如果当前后端是 FastAPI，则继续使用 FastAPI + SQLAlchemy + SQLite。如果当前前端是 Vite/React，则继续使用 Vite/React。不要为了炫技更换框架。
```
